# 기록 크기·내보내기·저장 실패

2026-09-09 G07. `python3 scripts/archives.py list --limit 50`으로 `var/` 바로 아래의 terminal ANSI·입력 JSONL·session TXT 개수와 총 바이트를 확인한다. 파일 내용은 읽지 않고 표시 행만 제한한다. 하위 의존성·CLI 자체 대화 DB·진단 자료 용량은 포함하지 않는다. 이번 관찰은 235개, 1,456,779,316바이트였다.

## 원본을 유지하는 내보내기

CLI를 정상 종료한 뒤 다음처럼 파일을 지정한다.

```sh
python3 scripts/archives.py export var/terminal-실제파일.ansi /백업경로/대화.ansi
```

목적지 디렉터리는 미리 준비한다. 1MiB 청크로 최초 크기만큼 읽어 목적지 디렉터리의 임시 파일에 기록하고 fsync·SHA256 대조 후 게시한다. 원본의 inode·크기·mtime·ctime 변경을 감지하면 거절한다. 목적지 기존 파일은 덮어쓰지 않으며 원본은 삭제하지 않는다. 임시 파일은 0600이고 실패 시 자신이 만든 임시 파일만 정리한다. 심볼릭 링크 원본은 받지 않는다. 링크 게시를 지원하지 않는 파일시스템에서는 오류로 끝날 수 있다.

살아 있는 기록의 복사를 완전한 대화 스냅샷으로 보장하지 않는다. 한 파일의 검사와 게시 사이에도 원본이 바뀔 수 있으므로 먼저 CLI를 종료한다. ANSI와 `.ansi.input.jsonl`을 함께 보관하려면 각각 내보낸다. 두 파일의 트랜잭션은 아니다. 디렉터리 게시의 전원 장애 내구성까지 보장하지 않는다.

## 보관과 정리

자동 삭제·보관 기간 제한은 없다. 원본을 정리하고 싶다면 해당 CLI를 닫고 필요한 파일을 내보내 SHA256과 내용을 확인한 뒤, `M-x dired`에서 선택한 원본만 삭제한다. 이는 사용자 선택에 따른 보관 위치 이동이며 앱이 전체 기록을 임의로 버리는 정책이 아니다. CLI 대화 재개를 유지하려면 제공자 자체 대화 저장소도 필요하다. ANSI 내보내기는 그 저장소의 백업이 아니다.

## 실패 검사

- 실제 임시 파일 권한 0400에서 기록 쓰기 실패: CLI 중단, 이전 기록 내용 유지, 실패 청크 미표시 확인.
- 부분 쓰기 뒤 ENOSPC를 **오류 주입**: 이전 기록과 쓰인 4바이트 `PART`는 남고 나머지는 기록되지 않음. CLI 중단, 전체 실패 청크 미표시 확인. 실제 디스크를 가득 채운 검사는 아니다.
- 기존 두 PTY 검사에서 실패한 세션만 중단되고 다른 세션은 기록·입력을 계속하는 것을 확인했다.
- 내보내기: 24MiB 파일 복사·SHA256 일치, Python 추적 할당 peak 4MiB 미만, 기존 대상 거절, 복사 중 원본 증가 거절, fsync ENOSPC 주입 시 미게시·원본 유지 검사 3개 통과. 이 메모리 수치는 프로세스 전체 RSS가 아니다.
- 종료된 실제 Codex 기록 `var/terminal-QzjFHR.ansi`를 `var/archive-exports/resume-codex-20260909.ansi`로 내보내기도 성공했다.

재현: `python3 tests/archive-tools-test.py`; Emacs `tests/storage-failure.el`의 `emacs-ai-storage-` ERT 선택 실행. 결과 `var/storage-failure-20260909.log`. 제품 기록 방식 자체는 변경하지 않았다.

PTY 원본은 수신한 바이트다. 직접 키 입력 전체, CLI가 별도 파일로 보낸 로그, OS가 전달하지 못한 출력까지 복구하지 못한다. 쓰기 실패가 난 마지막 청크는 일부만 디스크에 남을 수 있다. 터미널 기록에 fsync·전원 장애 무손실 보장은 없다.

## 실제 용량 부족·프로세스 충돌 추가 검사

`tests/run-full-volume.py`가 32MiB HFS+ 이미지 하나를 `/private/tmp/ai-enospc-*/volume`에 마운트했다. 실행 중 가짜 PTY 하나만 이 볼륨에 기록하고 다른 PTY는 일반 임시 폴더에 기록한다. 볼륨 크기와 마운트 지점을 검증한 뒤 제한된 볼륨만 채웠다. 실제 `Write error: No space left on device`가 발생했고 실패한 PTY 중단·이전 기록 prefix 보존·실패 청크 미표시·다른 PTY의 Enter 출력 기록과 생존을 확인했다. ERT 1개 통과. 호스트 디스크를 채우지 않았다.

이미지는 검사 종료 후 분리하고 임시 디렉터리도 삭제했다. `hdiutil info`와 임시 폴더 조회로 자기 시험 이미지 잔존 없음 확인. 최초 시도의 hdiutil 옵션과 Lisp 괄호 오류를 수정한 뒤 통과했으며 실패 실행에서도 이미지 분리를 확인했다. 로그는 `var/real-enospc-20260909.log`다.

`tests/archive-crash.py`는 일반 기록 작성 중인 별도 배치 Emacs에 SIGKILL을 보내 완료 확인된 첫 append의 바이트가 보존됐는지 검사했다. 새 Emacs에서 기록을 128자 상한·undo 비활성으로 재열기도 성공했다. 결과는 `var/archive-crash-20260909.json`이다. 이 검사는 OS가 살아 있는 프로세스 충돌이며, 전원 장애나 아직 완료되지 않은 쓰기의 전부 보존을 증명하지 않는다. AI CLI나 사용자 Emacs를 종료하지 않았다.
