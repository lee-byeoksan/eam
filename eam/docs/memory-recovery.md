# 출력 부하 뒤 메모리 회수

2026-09-09 G08. 이전 1시간 검사에서 후반 physical footprint 증가가 있어, 같은 Emacs에서 세션을 닫으면 회수되는지 추가 조사했다. 실제 PTY의 가짜 스트림을 사용했고 AI 호출은 없다. 이전 실제 CLI 유휴 메모리와 분리한 Emacs/Ghostel 측정이다.

## 검사와 결과

첫 실행은 4세션×8초 스트림을 4회 반복했다. 각 회차의 출력 완료, GC, Close, GC 뒤를 측정했다. Close+GC에서 대략 3~4MiB가 회수됐지만 정리 후 기준값은 약 35.2→40.8MiB로 증가해 이 실행만으로 판단하지 않았다. `var/memory-recovery-20260909/samples.jsonl`에 있다.

두 번째 실행은 4세션×4초를 16회 반복하고 타이머 처리 후 GC를 한 번 더 했다. 측정 자체가 시계열을 Emacs 안에 누적하지 않도록 한 행씩 디스크에 추가한다. 프로세스 객체 수도 별도 기록했다.

- 정리·추가 GC 후 footprint 첫 회 약 35.52MiB, 마지막 약 36.22MiB. 16회 범위 약 35.52~38.53MiB.
- 프로세스 객체 1개(로컬 편집기 서버), 세션 0개, 타이머 0개, 버퍼 6개로 유지됐다. 반복에 따라 종료 프로세스 객체가 쌓이지 않았다.
- 첫 실행의 상승이 같은 모양으로 계속되지 않았다. 메모리 일부 회수와 일정 범위 내 변동은 확인했으나 allocator 보유분·모든 네이티브 할당을 분해한 결과는 아니다.
- 네이티브 CLI 메모리는 이 숫자에 포함하지 않았다. [기존 실제 4 CLI 측정](cli-model-and-soak.md)과 같은 측정값으로 합산하지 않는다.

[시계열](cli-validation-evidence/memory-recovery/samples.json), [요약](cli-validation-evidence/memory-recovery/summary.json). 프로브는 `tests/memory-recovery.el`, OS 읽기는 기존 `tests/process-footprint.py`다. Emacs/PTY를 정상 정리하고 프로브가 exit 0으로 끝났다.

## 발견한 시작 경로 문제

긴 결과 폴더 이름에서 `Service name too long`이 발생했다. macOS Unix 소켓 길이 제한 때문이었다. 메모리 확장 검사는 짧은 `var/rec16-0909` 경로에서 진행했다.

제품은 프로젝트 내 소켓 경로가 100바이트 이상이면 `/tmp/emacs-ai-editor-*`의 전용 0700 디렉터리를 사용하도록 수정했다. 기록 파일 위치는 그대로다. 정상 종료에서 자신의 빈 임시 디렉터리만 정리하고, 다른 서버 디렉터리를 지우지 않는다. 강제 종료 뒤 빈/소켓 디렉터리가 남는 경우는 가능하다.

100자 접두사의 기록 경로에서 실제 가짜 CLI 외부 편집기 왕복과 64KiB 전달 검사를 실행해 터미널 회귀 5개 통과. 시험 임시 소켓 디렉터리도 종료 후 없음을 확인했다. 메모리 두 실행은 이 소켓 수정 전 코드에서 수행됐으며, 소켓 수정은 별도 회귀로 검증했다.

## 남은 범위

수십 초 반복 결과를 수시간 안정성·GUI 입력 지연·스크롤 프레임 지연이나 이전 1시간 footprint 상승의 완전한 원인 규명으로 확대하지 않는다. 장시간 GUI와 최신 코드의 종합 안정성 확인은 아직 남는다. 이번 결과로 메모리 누수를 단정하거나 근거 없이 강제 GC를 제품에 추가하지 않았다.
