# 로컬 테스트 패키지 준비

사용자는 직접 테스트하면서 패키지화를 진행하기로 했다. G10의 후속 범위이며, 원래 GUI·IME 검증은 별도로 남아 있다. 우선 현재 Apple Silicon macOS / Emacs for Mac OS X 환경용으로 준비한다. 공개 패키지 저장소 게시나 다른 OS 지원은 아직 포함하지 않는다.

## 준비 순서와 완료 기준

1. 코드·문서·보조 프로그램 위치를 대화 기록 위치와 분리한다. 기록 폴더를 바꿔도 매뉴얼·프로젝트 선택·검색이 동작해야 한다.
2. Ghostel 원본 의존성·네이티브 모듈과 Python 보조 프로그램의 설치 위치를 정한다. 설치된 의존성을 사용할 수 있어야 하며, 패키지 로드만으로 다운로드하거나 AI를 실행하지 않는다.
3. 패키지 메타데이터·autoload·버전과 설치 산출물을 준비한다. 개인 대화·인증·실험 데이터·생성된 앱 번들은 포함하지 않는다.
4. 임시 설치 위치의 새 `-Q` Emacs에서 설치→시작 화면→기록 열기/검색→PTY·외부 편집기 왕복을 검증한다. 작업 저장소를 우연히 참조해 통과하지 않도록 확인한다.
5. 설치·업데이트·제거 안내와 독립 실행 방법을 제공한다. 코드 업데이트나 패키지 제거가 기록을 삭제하지 않는지 확인한다. 개인 init 파일은 자동 수정하지 않는다.

## 현재 구현

2026-09-09 첫 경로 분리:

- `eam--resource-directory`로 설치된 코드·문서의 기준 위치를 고정했다. 시작 화면과 사용 안내는 기록 폴더와 독립적으로 이 위치를 사용한다.
- 외부 편집기 실행은 현재 Emacs의 실행 디렉터리 아래 `bin/emacsclient`, 같은 디렉터리의 `emacsclient`, PATH 순서로 찾는다. 필요하면 `eam-emacsclient-executable`로 지정한다. 명시한 경로가 잘못되면 다른 클라이언트로 조용히 대체하지 않고 서버 시작 전에 오류를 표시한다.
- 앱 회귀 6개와 실제 PTY/외부 편집기 회귀 6개 통과. 기록 위치를 다른 경로로 바꿔도 안내 버튼이 실제 매뉴얼을 가리키는 검사와 잘못된 클라이언트 경로에서 서버를 시작하지 않는 검사를 추가했다.

패키지로 일반 로드할 때 기록 기본값은 `user-emacs-directory` 아래 `eam/`다. 기존 독립 GUI 런처는 `eam-standalone`을 명시적으로 로드해 프로젝트 `var/`를 유지한다. Ghostel은 이미 load-path에 설치돼 있으면 그것을 사용하며, 없을 때만 기존 프로젝트 `var/deps/ghostel/lisp`를 찾는다. 로딩 단계의 다운로드는 없다.

`python3 tests/package-paths.py`로 한글·공백이 있는 별도 설치 폴더에 Lisp와 매뉴얼을 복사하고, 새 배치 Emacs 두 개에서 일반/독립 로딩의 서로 다른 기록 경로와 설치 리소스 경로를 검사했다. 미리 설치된 Ghostel 경로를 명시해 사용했으며 설치 폴더의 var·사용자 프로필·프로세스가 로딩만으로 생성되지 않았다. 이는 설치 tar의 package-install-file 검증은 아니다. 기존 일반 회귀(Python 5개·ERT 11개), 앱 6개, 터미널 6개도 통과했다.

설치용 tar 패키지는 아직 없다. 다음 작업은 패키지 메타데이터·autoload·의존성 선언과 설치 산출물을 만들고 package-install-file 및 제거 후 기록 보존을 검증하는 것이다. 현재 경로 검사만으로 패키지화 완료를 주장하지 않는다.


## 0.1.0 설치 산출물

`var/packages/eam-0.1.0.tar`를 생성했다. `python3 scripts/build-package.py`로 재현하며, 같은 파일이 있으면 덮어쓰지 않는다. 다른 스냅샷은 `--output-dir`로 별도 디렉터리를 지정한다. Lisp 제품 파일·Python bridge 2개·정적 Markdown 문서와 SHA-256 manifest를 포함한다. 대화 기록, 테스트 데이터, 인증 파일, Ghostel 소스/바이너리, 개인 앱 번들은 포함하지 않는다. 정적 문서의 시험 증거 링크 대상은 패키지에 포함되지 않아 개발 저장소에서 확인해야 한다.

Emacs 30.1과 Ghostel 0.53.0 이상을 패키지 의존성으로 선언했다. 검증한 Ghostel은 0.53.0이며 이후 버전 전체 호환을 보증하지 않는다. 네이티브 모듈과 공식 CLI/Python은 외부 실행 의존성이다.

`python3 tests/package-install.py var/packages/eam-0.1.0.tar` 통과: 한글·공백 설치 폴더에서 실제 `package-install-file`, 시작 화면 autoload, 제품 Lisp 바이트 컴파일, 설치 위치의 비동기 검색 도구와 정확한 바이트 offset, `package-delete` 후 외부 데이터 폴더의 한글 기록 보존을 확인했다. 첫 실행은 시험 의존성의 메타데이터만 등록해 Ghostel 로딩 실패가 났고, 원본 Ghostel의 실제 load-path도 등록한 후 통과했다. 로그는 `var/package-install-0.1.0-retry.log`다.

이 검사는 기존 원본 Ghostel 설치를 수동 등록한 격리 환경에서 수행했다. 사용자의 개인 Emacs에 설치하지 않았고 upstream Ghostel을 패키지 관리자로 설치하는 흐름까지 검증한 것은 아니다. 다음은 Ghostel 준비를 포함한 사용자의 설치 절차와 설치된 코드의 PTY/외부 편집기 통합 검증이다. 배포물의 생성·검색·제거 성공을 전체 패키지 사용 검증으로 확대하지 않는다.


후속: 설치된 패키지에서 PTY 회귀 6개와 제품 함수의 symbol-file이 설치 폴더 아래인지 검증했다(`var/package-install-pty-0.1.0.log`). `scripts/prepare-package-profile.py`로 원본 Ghostel·모듈 해시를 확인하고 새 격리 프로필을 준비한다. 첫 프로필에서 수동 의존성의 autoload 파일 부재 경고를 발견해 Ghostel 명시 로딩·활성 등록으로 수정했다. 수정된 새 `var/package-profile-ready`는 설치·새 Emacs 로딩 검증 통과, GUI 미실행. [바로 실행하는 방법](package-testing.md). upstream 패키지 저장소 설치 대신 현재 로컬 원본 의존성을 재사용하는 프로필이며, 자동 업데이트·기록 마이그레이션과 최신 GUI 검증은 완료하지 않았다.


2026-09-10 0.1.1: 설치 폴더를 프로젝트 기본값으로 삼는 진입 문제 수정. 앱은 호출한 버퍼의 default-directory를 유지하고 문서만 설치 리소스에서 연다. 실제 package-install-file 검사에 해당 경로 보존 조건을 추가했으며 설치된 코드의 PTY 6개·기록 검색·제거 보존 통과. 수정 프로필은 var/package-profile-0.1.1, 기존 0.1.0 설치/기록 미변경. 준비 스크립트의 기본 버전은 소스 헤더에서 읽는다.
