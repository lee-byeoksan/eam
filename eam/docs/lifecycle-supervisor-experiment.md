# 외부 감시자 실험과 결정

2026-09-08. 상태: **프로토타입 검증 완료, 기본 앱 적용 보류**. CLI와 Emacs 밖에서 실행되는 감시자는 미리 관찰한 작업을 정리했지만, 빠르게 분리된 작업을 놓치는 반례도 재현됐다. ‘전체 작업 정리’의 완료 조건은 충족하지 못했다.

## 문제와 비교한 방법

실제 Claude·Codex 강제 종료 뒤 실행 중 명령이 남는 [앞선 결과](terminal-exit-limits.md)를 해결하기 위한 실험이다. 공식 대화형 CLI와 PTY를 유지하고 개인 설정·프롬프트·스킬에 관여하지 않는 조건으로 비교했다.

| 방법 | 장점 | 탈락 조건 또는 비용 |
| --- | --- | --- |
| 프로세스 그룹 종료 | 단순하며 정상적인 같은 그룹 작업에 적용 가능 | `setsid`로 분리된 작업은 경계 밖으로 나감. 이전 실험에서 생존 확인 |
| 외부 감시자 + 관찰한 PID/시작 시각 | CLI/Emacs 충돌 뒤에도 살아서 이미 추적한 작업 정리 가능 | 관찰 사이에 부모가 사라지는 경우 누락. 이번 반례로 전체 추적 가정 기각 |
| 실행 전 작업 등록 또는 OS가 강제하는 작업 경계 | 생성 시점에 소유권을 확보하는 방향 | 임의의 네이티브 CLI 자식까지 포함하려면 별도 연동·OS 지원을 확인해야 함. 이번에 구현·검증하지 않음 |

Apple의 [launchd 설정 설명](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5)의 `AbandonProcessGroup`도 같은 프로세스 그룹의 잔여 작업에 대한 동작이다. 외부 실행 주체를 launchd로 바꾸는 것만으로 별도 세션까지 해결된다고 간주하지 않는다. 설치된 Apple SDK `sys/event.h`에는 `NOTE_TRACK`, `NOTE_TRACKERR`, `NOTE_CHILD`가 10.5부터 지원되지 않는다고 명시되어 있다. kqueue의 이름만 보고 fork 계보 자동 추적을 가정하지 않았다.

## 구현 범위

- [감시자](../experiments/lifecycle/watchdog.py)는 독립 시험 제어기가 새 OS 세션으로 실행한다. 기존 앱·Ghostel의 CLI 시작 코드는 바꾸지 않았다.
- macOS `libproc`로 50 ms마다 같은 사용자의 PID·부모 PID·시작 시각을 읽는다. 명령 문자열이나 환경 변수는 조회하지 않는다.
- CLI 루트부터 관찰한 계보를 확장하고, 이미 관찰한 프로세스는 부모가 바뀌어도 PID와 시작 시각이 같으면 유지한다. 종료된 항목은 제거한다.
- CLI 또는 소유 Emacs가 종료되면 관찰한 작업에 TERM을 보내고, 2초 유예 후 남은 작업에 KILL을 보낸다. 신호 직전 신원을 다시 검사한다.
- 시험은 루트와 자식이 살아 있는 동안 감시자 연결을 확인한 뒤 종료한다. **실제 CLI 시작 직후의 관찰 공백까지 해결한 구현이 아니다.**
- 유지할 작업 대조군은 처음부터 세션 트리 밖에서 별도로 시작했다. 세션 내부 작업을 ‘유지’로 전환하는 기능이나 실제 공유 데몬 식별 기능은 구현하지 않았다.

## 결과

실제 Emacs 30.1/Ghostel PTY 안에서 가짜 CLI를 실행했다. 각 CLI는 일반 자식과 TERM을 무시하는 별도 세션 자식을 만든다. 다른 Emacs 시험 세션과 별도 유지 작업을 동시에 실행한 상태에서 검사했다.

| 조건 | 미리 관찰한 작업 정리 | 다른 세션·별도 유지 작업 | 판정 |
| --- | --- | --- | --- |
| 앱 Close | 모두 더 이상 실행하지 않음, 분리 자식 KILL 확인 | 계속 동작 | 제한된 범위 통과 |
| CLI SIGKILL | 동일 | 계속 동작 | 제한된 범위 통과 |
| Emacs 정상 종료 | 동일 | 계속 동작 | 제한된 범위 통과 |
| Emacs SIGKILL | 동일 | 계속 동작 | 제한된 범위 통과 |
| 관찰 공백 중 double-fork/setsid 후 CLI SIGKILL | 기존 관찰 작업만 정리, **새 고아 작업 생존** | 계속 동작 | 전체 추적 가정 반증 |

반례에서는 감시자만 SIGSTOP으로 잠깐 멈춘 동안 fixture가 double-fork/setsid를 수행하고 중간 부모를 종료했다. 자식의 부모가 PID 1로 바뀐 것을 확인한 뒤 감시자를 재개했다. 여러 관찰 주기가 지나도 이 자식은 소유 목록에 들어가지 않았고, CLI 종료 뒤 heartbeat가 계속 변했다. 의도적으로 관찰 공백을 만든 결정적 반례이며, 평상시 발생 빈도나 확률을 측정한 시험은 아니다. 조회 주기를 줄여도 공백 자체가 사라지지는 않는다.

감시자의 `remaining_observed: []`와 실제 미관찰 작업 생존이 동시에 나타났다. 따라서 **‘관찰한 잔여 작업 0’은 ‘전체 잔여 작업 0’이 아니다.** 결과에는 `complete_tree_guarantee: false`를 명시했다.

[기계 판독 결과](cli-validation-evidence/supervisor/results.json). 각 실행의 감시자 전체 경과 시간은 약 3.04–3.36초이며, 연결·종료 대기·유예·최종 확인을 포함한다. 순수 종료 지연 수치가 아니다. 고아 작업은 시험 제어기가 알고 있는 신원으로 따로 종료했고, 제어군을 포함해 시험이 기록한 프로세스의 생존 목록은 최종적으로 비었다.

추가 확인:

- PID 재사용 시 새 자식에게 소유권을 넘기지 않음, 재부모화된 기존 자식 유지, 신호 직전 PID 재사용 거절, 조회 권한 오류를 종료로 오인하지 않음: 단위 검사 4개 통과.
- 기존 터미널 입력/외부 편집기 왕복과 기록 실패 격리: ERT 2개 통과.
- Python 문법 검사와 수정된 Lisp 괄호 검사 통과.
- **AI 요청 0회, GUI 실행 없음.** 물리 키보드의 한글 조합·스크롤·UI 반응, 감시자 장시간 CPU/메모리는 이번 검증 대상이 아니다.

## 자체 검토와 결정

별도 모델 호출 없이 자체 반대 검토를 수행했다. 독립 리뷰를 받은 것으로 기록하지 않는다.

1. 부모 사망 후에도 소유 관계를 알 수 있다는 가정은 사전에 관찰한 작업에만 성립한다. 반례 때문에 제품의 완전한 종료 경계로 채택하지 않는다.
2. PID와 시작 시각 검사는 PID 재사용 위험을 줄이지만, 프로세스 조회는 원자적인 전체 스냅샷이 아니며 신원 검사와 `kill` 사이에도 경쟁 구간이 있다. OS의 원자적 프로세스 핸들을 대신하지 않는다.
3. 감시자 자신이 죽으면 이 구현의 정리 주체도 사라진다. 자동 재시작이나 소유권 복구는 구현하지 않았다.
4. 세션 밖에서 실행한 유지 작업이 살아 있는 것만으로 모든 공유 데몬·사용자가 유지하려는 작업을 식별했다고 주장하지 않는다. 특히 세션에서 처음 만들어져 다른 세션도 쓰게 된 데몬은 별도 정책이 필요하다.

**결정:** 실험 코드를 `experiments/`에 두고 기본 앱에 연결하지 않는다. 불완전한 기반 위에서 Claude/Codex에 같은 시험을 추가하면 전체 정리 가정을 검증할 수 없으므로 실제 AI 연결 재시험은 이번에 진행하지 않았다. 앞선 실제 CLI 작업 잔존 제한은 그대로 유효하다.

후속 순서는 정상 종료 시 CLI 고유의 작업 중단·목록 확인으로 어디까지 정리할 수 있는지부터 검증하고, 세션 종료의 의미와 남는 작업을 사용자가 확인할 수 있게 정리하는 것이다. 충돌 시 임의의 모든 하위 작업 정리는 별도 미해결 항목으로 유지한다. 강한 정리 보장이 필요하다면 실행 전 등록이나 OS가 강제하는 경계의 실제 적용 가능성을 먼저 검증해야 한다.
