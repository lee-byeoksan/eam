## 해석과 한계

확인한 것은 출력 버퍼와 페이지 읽기량의 상한, 짧은 실험에서의 기록 무손실이다. RSS가 고정된다는 결론은 아니다. 특히 첫 페이지 조회 실험은 RSS를 약 26MiB 늘렸다. 추가 조회에서 증가폭은 작아졌지만 장시간 누수 부재를 증명하지 않는다.

RSS에는 Emacs 런타임·할당자 잔류 메모리·버퍼 저장소가 포함되고, GC 객체 추정치는 RSS나 전체 heap 크기가 아니다. 시간 표본 리스트도 측정 중 유지되어 객체 증가 일부를 차지한다. 세션 수 실험은 같은 프로세스를 재사용하므로 각 행의 RSS를 독립 프로세스의 세션당 비용으로 해석하면 안 된다. CPU 점유율, 에너지, 장시간 soak, 느린 디스크, 대형 입력 undo, 여러 GUI 창, 실제 프로토콜 출력 폭주는 측정하지 않았다.

현재 가짜 생성기는 처음부터 배치 단위로 문자열을 만든다. 실제 프로세스 filter의 분할 바이트 수신·큐 밀림·역압 처리는 검증 대상이 아니다. 사용자 입력과 undo는 의도적으로 보존하므로 출력 상한만으로 앱 전체 메모리에 상한이 생기지는 않는다.

### GUI 상태와 메모리

보고 파일은 GUI의 `Save report` 메뉴를 눌러 저장했다. 13세션(12개 동시 생성 + 기존 완료 1개)의 최종 디스크 기록 합은 **77,933,184바이트**였다. 과거 화면을 유지한 최종 스냅샷의 출력 문자 합은 **766,919**이며 모든 버퍼가 상한 이하였다. 입력 undo는 모두 유지, 출력 undo는 모두 비활성, 오류는 모두 nil이었다.

GUI 프로세스의 단발 `ps` 표본은 진행 중 RSS **179,504KiB / CPU 42.9%**, 완료 후 **168,208KiB / CPU 0.0%**였다. 기준 RSS·장시간 시계열·GC 통제가 없으므로 세션당 메모리 비용이나 안정화 지표로 해석하지 않는다. Computer Use 왕복 시간도 입력 지연 수치로 쓰지 않았다.

### 발견한 개선점과 다음 확인

1. **live 헤더의 바이트 범위가 갱신되지 않는다.** 초기 `LIVE | bytes 0–0`가 출력 중에도 남는다. 실제 기록은 계속 저장되며 보고값으로 확인했으나 UI 표시는 오해를 부른다. 이 GUI 검증에서는 운영 코드를 수정하지 않고 발견 사항으로 남겼다.
2. **한글 입력은 아직 통과가 아니다.** 다음 실험은 동일 입력 소스에서 일반 `text-mode`와 프로토타입 입력 버퍼에 같은 키를 보내 비교해야 한다. 실제 키보드와 Computer Use의 결과도 구분해야 한다.
3. live 상태에서 상한을 넘으면 오래된 내용이 삭제되어 읽는 위치가 밀리는 동작을 관찰했다. 오래된 구간을 고정해서 읽을 때는 history 모드를 사용해야 한다.

모든 가짜 스트림은 종료된 상태로 두었다. 테스트 전용 GUI 창과 기록은 재검토할 수 있도록 남겼다. 실제 AI 연결은 수행하지 않았다.
