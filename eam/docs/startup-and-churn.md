# 시작 실패 정리와 반복 세션 검증

2026-09-08. CLI 시작 과정에서 오류가 날 때 생성 중이던 터미널 버퍼가 남는 문제를 재현하고 수정했다. 이후 실제 가짜 PTY를 네 개씩 총 200회 생성·입력·종료했다.

## 수정

`emacs-ai-terminal-start`는 기록 파일·버퍼를 먼저 만들고 편집기 서버와 Ghostel을 준비한다. 이전 구현은 준비 도중 오류가 나면 만들어 둔 버퍼를 정리하지 않았다. 편집기 서버 준비 단계에 오류를 주입한 회귀 검사가 실제로 실패했다.

시작 완료 전에는 `unwind-protect`로 실패한 시작의 세션 등록·프로세스·버퍼를 정리한다. Ghostel이 PTY를 만들고 반환 전에 오류를 내는 경우에는 해당 출력 버퍼의 프로세스를 찾아 정리한다. 원래 오류는 호출자에게 전달하며 기록 파일은 삭제하지 않는다. 기존 정상 세션이나 공용 편집기 서버를 종료하지 않는다. 임의의 모든 하위 작업 정리 기능을 추가한 것은 아니다.

새 회귀 검사는 편집기 준비 실패, 실제 PTY 생성 뒤 실패, 표시 실패를 주입한다. 각 경우 버퍼 없음·새 살아 있는 프로세스 없음·세션 등록 원복·기존 CLI 생존·원래 오류 보존을 확인했다.

후속으로 일반 버퍼/원시 기록 조회 경로의 파일 열기 실패도 검사했다. 없는 기록 파일을 열 때 조회 버퍼 두 개가 남는 문제를 재현했고, `emacs-ai--create`에도 준비 실패 시 버퍼 정리를 적용했다. 기존 세션의 기록·출력이 유지되는 새 회귀 검사가 통과했다.

## 반복 생성·종료

`tests/terminal-churn.el`은 네 개의 실제 가짜 CLI를 시작해 한글·이모지·두 줄 입력을 전달하고 Enter 응답을 기다린다. 초안 버퍼를 닫아도 CLI가 살아 있는지 확인한 뒤, 회차별로 앱 Close / 출력 버퍼 kill / native Ctrl+C 후 Close를 번갈아 적용한다.

| 측정 | 결과 |
| --- | --- |
| 총 세션 / 동시 세션 | 200 / 4 |
| 경과 시간 | 약 8.74초 |
| 회차 종료 뒤 앱 세션 등록 | 매회 0개 |
| 측정 시 Emacs 버퍼 수 | 10개 표본 모두 5개 |
| 측정 시 살아 있는 Emacs process 객체 수 | 모두 1개, 편집기 서버가 열린 상태 |
| 20회 / 200회 후 GC 뒤 RSS | 49,664 / 50,960 KiB, 약 48.5 / 49.8 MiB |
| 종료 대상의 프로세스·초안·출력 버퍼 | 200회 모두 남지 않음 |

타이머 수는 표본에서 3 또는 5개였고 누적 증가하지 않았다. 모든 OS 자식의 계보를 조사한 수치는 아니다. 짧은 반복 생성에서 버퍼·등록·주 CLI가 누적되지 않는 것을 검증했으며, RSS 증가가 전혀 없거나 수시간 누수가 없다고 결론 내리지 않는다. 장시간 출력 유지 검사는 별도다.

증거: [표본](cli-validation-evidence/startup-and-churn/samples.json), [결과](cli-validation-evidence/startup-and-churn/result.json), [시작·실행 준비 검사](cli-validation-evidence/startup-and-churn/startup-checks.json).

기본 Python 검사 5개·ERT 8개, 터미널 ERT 3개 통과. 기본 검사의 첫 실행은 실행 샌드박스가 `ps`를 막아 실패했고, 허용된 환경의 동일 검사로 통과했다. 터미널 파일은 Ghostel load-path를 포함한 경고=오류 byte compile을 통과했다. 컴파일 결과 파일은 삭제해 이후 실행이 소스를 로드하도록 했다.

추가 수정 뒤 기본 검사는 Python 5개·ERT 9개로, 터미널 검사는 ERT 4개로 증가했으며 모두 통과했다. 추가 터미널 검사는 빈 외부 편집기 입력과 정확히 65,536바이트인 한글·이모지 전달을 확인한다. 65,537바이트 초안은 사용자 입력과 전송 기록을 변경하지 않고 거절한다. 가짜 CLI에서 빈 외부 편집을 허용하도록 미정의 초기 입력 변수도 빈 문자열로 초기화했다. 제품에서 발견한 빈 편집기 결함으로 세지는 않는다.

설치된 Ghostel 모듈 해시와 시험용 앱 준비 스크립트도 확인했다. 앱 ID 분리, `-Q`, 현재 시험 driver, 설치 Emacs와 같은 실행 바이너리, 원본 리소스 연결, 파일·URL 연결 등록 제거를 확인했다. **앱 준비는 GUI 실행이 아니다.** 이번에 GUI를 새로 열지 않았으며 물리 키보드 IME 결과로 기록하지 않는다.

## 재현

```sh
bash scripts/test-terminal.sh
EMACS_AI_CHURN_DIR="$PWD/var/새-churn-시험경로" \
  /Applications/Emacs.app/Contents/MacOS/Emacs --batch -Q -L lisp \
  -l tests/terminal-churn.el
```

PTY·로컬 소켓·프로세스 조회가 허용된 환경이 필요하다. 가짜 CLI만 실행하므로 AI 요청은 없다. 이미 존재하는 churn 결과 폴더는 재사용하지 않는다.

## Ghostel 모드 전환 뒤 메뉴 소실 수정

앱이 최초 Ghostel 로컬 키맵에만 메뉴를 붙여 두어 복사 모드로 전환하면 `Terminal AI`가 사라지는 문제를 실제 가짜 PTY 회귀 검사로 재현했다. 앱 메뉴를 버퍼별 `emacs-ai-terminal-controls-mode`의 키맵에 두어 Ghostel의 로컬 키맵 교체와 독립적으로 유지한다. 개인 Emacs 설정이나 Ghostel 원본을 변경하지 않는다.

복사·Emacs·문자·기본 입력 모드를 순서대로 전환해 메뉴가 유지되는 것을 확인했고, 이후 입력·외부 편집기 왕복도 통과했다. 터미널 ERT는 총 4개 모두 통과했다.

실제 GUI에서는 이번에 별도 `Emacs AI Terminal Test`의 가짜 CLI를 열어 확인을 시도했다. 합성 Ctrl 키가 의도한 전환 대신 `C-l is undefined`로 표시되어 모드 전환 성공으로 세지 않았다. 이후 메뉴 열기에서 Computer Use가 `cgWindowNotFound`를 반환했고, Escape·앱 ID·앱 경로 재조회도 실패했다. API의 앱 목록은 실행 중이라고 반환했지만 화면을 다시 확인할 수 없어 **GUI 메뉴 유지 검사는 미완료**다. 원인이 Emacs 결함인지 도구의 창 인식 문제인지 이 결과로 단정하지 않는다.

`tests/terminal-gui.el`에는 `Terminal Test → Copy mode`와 `Return to terminal input`을 추가했다. 새 시험 GUI를 열면 합성 단축키 없이 같은 전환을 확인할 수 있다. 이 추가 메뉴는 검증용이며 대화형 AI를 시작하지 않는다. 기존 실행 중 인스턴스에는 새 코드가 자동으로 반영되지 않는다.

## 검증 도구의 종료 대기 보완

실제 CLI의 정상 종료가 1초보다 늦어 고정 대기 뒤 상태 검사가 실패한 사례가 있었다. 제품 종료 실패로 기록하지 않고, 검증 제어기에 `wait-exit --timeout 10`을 추가했다. 상태가 exit 또는 signal이 될 때까지 기다리고 기한을 넘으면 실패한다. 상태·화면 파일도 각 파일의 임시 파일 작성 후 rename으로 게시한다. 두 파일을 하나의 원자적 스냅샷으로 묶은 것은 아니다.

검증 driver에 `fixture` 제공자를 추가해 실제 계정 CLI 없이 도구 자체를 시험했다. 살아 있는 CLI에 대한 짧은 대기는 시간 초과, native 종료 뒤 대기는 성공했다. 상태 갱신 중 JSON 909회 읽기(서로 다른 스냅샷 4개), 검증 도구의 편집기 원문 읽기·쓰기·반환도 통과했다. [검사 결과](cli-validation-evidence/startup-and-churn/harness-checks.json). 실제 Claude/Codex를 실행하지 않았다.

## 종료한 터미널의 기록 재열기

2026-09-08 추가 검사 `emacs-ai-terminal-archive-survives-close`에서 가짜 PTY를 시작하고 한글·이모지·ANSI·CRLF 데이터를 기록 필터에 전달했다. Close로 PTY와 버퍼를 닫은 뒤 실제 기록 열기 명령으로 다시 열었다. 모든 이전 페이지를 합친 결과가 원문과 일치했고, 128자 제한 설정에서 각 파일 읽기 요청도 128바이트 이하임을 계측했다. 출력 undo 비활성, 조회 세션의 프로세스·타이머 없음, 파일 내용 유지도 확인했다. 터미널 ERT 총 5개 통과, 실행 로그는 `var/archive-regression-20260908.log`에 있다.

첫 실행은 비교 기준을 읽을 때 Emacs의 자동 CRLF 변환이 적용돼 실패했다. 비교 기준도 `utf-8-unix`로 읽도록 테스트를 수정한 뒤 통과했다. 제품의 원시 CRLF 보존 동작은 변경하지 않았다. 이 검사는 작은 ANSI 기록의 수명·전체 페이지 복원을 다루며, 큰 기록의 부하는 별도 1시간 검사에 있다. ANSI 화면 재구성이나 GUI 스크롤 성능을 검증한 것은 아니다.

같은 날 사용자가 “잘 되는 것 같은데”라고 보고했다. 긍정적인 사용 관찰로 기록하되, Computer Use의 창 인식 실패 원인 해소나 개별 물리 IME 시험 통과로 간주하지 않는다.
